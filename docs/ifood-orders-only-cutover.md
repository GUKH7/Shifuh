# Order + Events: staged transition (NOT authorization to deploy)

The production app has one central credential pair. `IFOOD_ORDERS_ONLY=true` is a server-wide capability restriction, intended for the official Order/Events application; leave unset for existing fixtures. `IFOOD_CUTOVER_PAUSED=true` blocks provider operations in the new build. Neither flag is changed by this PR. OAuth cache v2 uses environment + HMAC of credential pair and API origins; old rows are deliberately not reused. Do not delete historic tokens or rotate the encryption key. Never log secrets or use live credentials in CI.

Before cutover: independently validate official OAuth and merchant permission in the developer portal; do not treat OAuth alone as proof of merchant authorization. Stop external polling schedulers, block access to old deployment URLs and manual iFood routes, drain in-flight invocations and SQL/ACK leases; a deployment env flag is NOT a distributed fence for older deployments. Ensure no traffic, disable order and catalog sync, recheck binding and private ownership. The current ownership trigger rejects direct replacement even for service role. Do not disable or modify the trigger. An authorized admin transaction may remove the *live integration row only* and insert a disabled row for the new merchant under the same restaurant, retaining the original registry entry; first verify foreign-key dependencies and back up exact integration metadata. A failed insert must roll back the delete. Never move or rewrite historical orders/events; historical catalog links must remain unusable in orders-only mode. Rebinding must not auto-enable catalog or orders. Rollback requires a separately approved quiescent transaction, using the original saved metadata and credential pair, with both merchants permanently reserved for the same restaurant. Do not roll back after real orders arrive without a separate reconciliation plan.

A staged session-local admin procedure now lives in scripts/ifood-merchant-cutover-procedure.sql. It is NOT a migration and must NOT be run against production without separate approval. It archives the old row privately, serializes concurrent integration writes, checks expected disabled binding, existing ownership, references and outstanding leases, replaces the live row with the same ID using the existing trigger, and leaves both flags false. Its rollback is another quiescent transaction and refuses if current-merchant events exist. Historical catalog links and events are not rewritten. The local CI test uses loopback PostgreSQL only and exercises competing replacement, reserved target, active lease, SQL failure before commit and rollback. External traffic drain remains an operational prerequisite: the SQL transaction cannot revoke an HTTP request already sent by an old deployment. Do not enable official polling until all old deployments and manual routes are quiescent and credentials + Merchant are verified. No release authorized.
